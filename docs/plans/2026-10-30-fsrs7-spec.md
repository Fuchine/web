# FSRS-7 + per-user optimization in the browser (T3.1)

**Date:** 2026-10-30
**Roadmap:** T3.1 in `docs/ROADMAP_ENGENHARIA.md` (Fase 3, innovation 2)
**Evidence:** `docs/PESQUISA_MERCADO-2026-10-29.md` §5 innovation 2 (srs-benchmark:
log loss 0.3620 default vs 0.3401 per-user-optimized on FSRS-7)
**Status:** Implemented

## Libraries (verified on npm, 2026-10-30)

| Package | Version | License | Role |
|---|---|---|---|
| `ts-fsrs` | 6.0.0 (2026-10-28) | MIT | Scheduler. v6 `DefaultScheduler()` defaults to **FSRS-7** (34 weights, a `stabilityFast` trace, fractional-day intervals). v4.7.1 (what we had) was FSRS-5. |
| `@open-spaced-repetition/binding-wasm32-wasip1` | 0.6.0 (2026-10-28) | MIT | Optimizer: fsrs-rs compiled to WASI, published by the open-spaced-repetition org from the ts-fsrs monorepo. Trains and evaluates FSRS-7 (`computeParameters`, `FSRSBinding.evaluate` → `logLoss`, `rmseBins`; CSV input via `convertCsvToFsrsItems`). "Public beta" upstream, so the version is pinned exactly. |

**Why not `fsrs-browser`** (named in the roadmap): its latest release (6.6.0,
BSD-3) wraps fsrs-rs 6.6 and trains **FSRS-6** (21 weights, no fast trace).
Those weights cannot drive the FSRS-7 scheduler. The binding above is the
org's maintained FSRS-7 optimizer.

**Why the `wasm32-wasip1` flavour:** the default `wasm32-wasi` build is
threaded and needs `SharedArrayBuffer`, i.e. a cross-origin-isolated page
(`COOP: same-origin` + `COEP: require-corp`). COEP would block the YouTube
IFrame player. The threadless wasip1 build runs single-threaded in a Web Worker
and needs no isolation.

**Node.** Both packages declare `engines.node >= 24`; the repo, CI and Docker
images are on Node 22. Everything was exercised on Node 22.22 (unit, E2E, build,
`next start`) and works; moving the runtime to Node 24 is left to whoever owns
the images and CI (not changed here).

## Data (migration 0018)

- `sentence_cards`: `stability_fast double precision NULL`, `learning_step int
  NOT NULL DEFAULT 0`, `fsrs_model text NOT NULL DEFAULT 'fsrs-7'`;
  `elapsed_days`/`scheduled_days` → `double precision` (FSRS-7 intervals are
  fractional; `elapsed_days` is now computed by us, ts-fsrs v6 dropped it).
- `review_logs`: `last_review timestamptz NULL`, `stability_fast double
  precision NULL`, `learning_step int NOT NULL DEFAULT 0`, `fsrs_model text
  NULL` (null = written by ts-fsrs v4 / FSRS-5); day columns → `double
  precision`. Memory fields stay the card's **pre-review** values.
- `user_settings`: `fsrs_params jsonb NULL` (34 numbers; null = ts-fsrs
  FSRS-7 defaults), `desired_retention real NULL` (null = 0.9).

ts-fsrs's `scheduleStatus` is derived from `state` (`0 → new`, `2 → review`,
`1/3 → learning`) because Fuchine uses no suspension middleware; `cardId` is
`sentence_cards.id` (it seeds the fuzz, so fuzz is deterministic per card).

### Existing cards (migration-safe mapping)

Upstream's rule: do not reuse FSRS-5/6 state or invent `stabilityFast`; rebuild
FSRS-7 memory from the **complete** history, or keep the card on its old model.

1. New cards (`state = 0`): `stability_fast = 0` (the FSRS-7 new card).
2. Learned cards with complete history (`count(review_logs) = reps > 0`, true
   for every card mined in the app, since D6 logs every review transactionally):
   stay `fsrs-7` with `stability_fast = NULL`. On first touch (review queue,
   grading, settings) `rebuildMemory` replays the card's logs with
   `Reschedule.replay` and writes stability/stabilityFast/difficulty. Due date,
   counters and logs are untouched.
3. Learned cards without complete history: `fsrs_model = 'fsrs-5'` (SQL in the
   migration, same rule at runtime for rows inserted later). They keep being
   scheduled by FSRS-5 with its default weights and the user's retention.

Tested: unit (`packages/core/src/fsrs.test.ts`, a card in the old shape is
replayed and reviewed; an FSRS-5 card keeps scheduling), E2E (`e2e-fsrs.ts` §5),
and an upgrade run applying 0000–0017, inserting v4-shaped rows, then 0018.

## Per-user parameters

`createFsrs({ params, desiredRetention })` in `@fuchine/core` builds (and
caches) the scheduler. `reviewCardById` and the review queue load it per user.
Stored values are validated on write; on read an invalid stored value falls back
to defaults rather than breaking reviews.

Validation (`validateFsrsParams`): an array of exactly 34 finite numbers inside
ts-fsrs's FSRS-7 bounds (`checkFSRS7Parameters`). Out-of-bounds vectors are
rejected, never clipped. Retention: a number in [0.80, 0.95].

When the weights change, `PUT /api/settings/fsrs` replays the memory of every
learned FSRS-7 card under the new weights in the same transaction (as Anki
recomputes memory states); due dates are not moved.

## API

| Route | Notes |
|---|---|
| `GET /api/review/logs/export` | The user's own `review_logs` as the optimizer's CSV: `card_id,review_time,review_rating,review_state,review_duration` (epoch ms; rating 1–4; FSRS state before the review 0–3; duration not tracked → 0). |
| `GET /api/settings/fsrs` | Params (null = defaults), retention, range, recommended band, review count, minimum, workload preview. |
| `PUT /api/settings/fsrs` | `{ params?: number[34] \| null, desiredRetention?: number \| null }`; 400 on invalid input. |

Both are session-guarded (covered by `auth-coverage.test.ts`); PUT is a
same-origin mutation under the T2.6 middleware.

## UI (Settings → Review)

- **Desired retention** slider 0.80–0.95, step 0.01, default 0.90, the
  recommended 0.85–0.90 band drawn under the track. Saves on change (debounced).
- **Expected workload**: "≈ N reviews/day for your M learned cards", labelled
  as an **approximation**: the binding exposes no simulator/expected-workload
  call, so it is `Σ (1 + (1 − r)) / max(1, interval_i(r))` over learned cards
  (each card reviewed once per its model interval at retention r, plus one
  same-day relearn for the expected lapses). New cards and backlog are not
  included.
- **Optimize my schedule**: enabled at **≥ 400 reviews**. The optimizer
  documents no minimum (fsrs-rs trains on a handful of items), so this is the
  task's fallback figure. Clicking downloads the CSV, trains in a Web Worker
  (`lib/fsrs-optimizer.worker.ts`), evaluates log loss on the same reviews with
  the current params (before) and the fitted ones (after), and offers "Use these
  parameters" only when the fit improves. "Reset to defaults" clears them.

Optimizer settings: `modelVersion: "FSRS-7"`, `enableShortTerm: true`,
`numRelearningSteps: 1`, day rollover 04:00 in the browser's IANA timezone.
The before/after log loss is in-sample (evaluated on the training reviews).

## CSP / headers

No change. The CSP in `next.config.ts` has no `script-src`/`default-src`, so
`WebAssembly.compile` needs no `'wasm-unsafe-eval'`, and the worker and the
`.wasm` are same-origin assets emitted by webpack
(`_next/static/media/fsrs-binding.wasm32-wasip1.*.wasm`). If a `script-src` is
added later (the nonce hardening pass), it must include `'wasm-unsafe-eval'`
and `worker-src 'self'` (or `script-src 'self'`) for this page to keep working.
No COOP/COEP (see above).

## Measured

Real run in Chromium (Playwright) against `next start -p 3155`, user seeded with
`apps/web/scripts/seed-fsrs-revlog.ts` (a simulated learner who forgets faster
than the FSRS-7 defaults, scheduled by the defaults):

| Reviews | Training items | Log loss before (defaults) | After (fitted) | Train time |
|---|---|---|---|---|
| 1,698 (150 cards) | 1,548 | 0.4772 | 0.4708 | 101 ms |
| 10,103 (800 cards) | 9,303 | 0.4395 | 0.4367 | 604 ms |

Synthetic data, so the gain says the pipeline works end to end, not what real
learners will see; srs-benchmark's 0.3620 → 0.3401 is the population figure.

## Limits

- FSRS-5 cards (legacy without history) are not covered by the fitted weights.
- No server-side "optimal retention" (the binding exposes none); the slider
  plus the workload approximation replace it, and the recommended band avoids
  the known low-optimal-retention bias.
- Log loss is not persisted; it is shown at optimization time only.
